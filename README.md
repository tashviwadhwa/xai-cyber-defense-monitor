# XAI Cyber Defense Monitor

A multi-source threat monitoring system. It combines network traffic with login activity, gives every event a 0–100 risk score, maps it to MITRE ATT&CK, recommends a response, and explains every alert so an analyst can see *why* it fired.

It runs in two modes:

| | Replay demo | Live capture |
|---|---|---|
| Network data | UNSW-NB15: real packets recorded on a lab testbed, attacks generated by a simulation tool | **Real packets** captured on your laptop |
| Login data | Simulated | **Real** failed logins from Windows (event 4625) or Linux (auth.log) |
| Detection | Random Forest trained on labelled attacks (supervised) | Behavioural baseline learned from your own normal traffic (unsupervised) |
| Explanation | SHAP (TreeExplainer) | Exact per-feature deviation from normal |
| Real time? | No, a replay of pre-scored data | **Yes** |

## Setup (once)

Python 3.10–3.13.

```
cd xai-cyber-monitor
python -m venv venv
venv\Scripts\activate            (Windows)
source venv/bin/activate         (Mac/Linux)
pip install -r requirements.txt
```

For live capture on Windows, also install **Npcap** from https://npcap.com/#download (keep the default options).

## Replay demo

```
python run_pipeline.py     # trains 4 models, simulates logs, scores and explains (~3 min)
streamlit run app.py
```

## Live capture (two laptops on the same Wi-Fi or hotspot)

**Laptop A (monitored)**, in a terminal opened **as Administrator**:
```
python live_monitor.py --learn 10
```
It prints this laptop's IP. For 10 minutes, use the laptop normally (browse, watch a video) while it learns what normal looks like. When it prints `DETECTING`, open a second terminal and run `streamlit run app.py`, then go to the **Live capture** tab.

**Laptop B (attacker)**, a normal terminal:
```
python attack_demo.py <laptop A's IP> scan     # port scan
python attack_demo.py <laptop A's IP> brute    # wrong-password logins over SMB (Windows)
python attack_demo.py <laptop A's IP> all      # both together, which should reach Critical
```
Only ever run `attack_demo.py` against your own devices.

Later runs of `python live_monitor.py` reuse the saved baseline. Use `--relearn` to learn again, for example on a different network.

**If something doesn't show up:**
- *No traffic from laptop B at all:* some phone hotspots isolate devices from each other. Try another hotspot or a Wi-Fi router, and check that `ping <laptop A's IP>` works from B.
- *No failed logins:* make sure Windows records them. In an Administrator terminal: `auditpol /set /subcategory:"Logon" /failure:enable`.
- *SMB brute force doesn't reach laptop A:* the network needs to be set to Private with file sharing on. If that's not possible, type a wrong password at laptop A's lock screen 10 times instead. It appears as a brute force from "local console".
- *Wrong network interface:* run `python live_monitor.py --iface "Wi-Fi"` (use your adapter's name).

## Results

**Replay model (held-out test set, 52,603 flows)**

| Model | Type accuracy | Detection | False alarms |
|---|---|---|---|
| Logistic Regression | 76.8% | 96.7% | 11.9% |
| Decision Tree | 81.4% | 98.4% | 14.0% |
| Gradient Boosting | 82.4% | 96.7% | 8.6% |
| **Random Forest (chosen)** | **82.4%** | **97.0%** | **8.4%** |

With correlation in the replay, 99.6% of real attacks raised an alert, and only 3.7% of normal flows did.

**Live mode (tested with a real port scan and brute-force attempts)**
A 1,000-port scan scored about 9 "spreads" above normal (anything above 3 is unusual) and was labelled Port scan. Brute-force sources were flagged High, and normal traffic stayed at a score of 0.

## Features

- **Detection:** supervised Random Forest (replay) and an unsupervised behavioural baseline (live).
- **Correlation:** network evidence + failed logins + repeat alerts from the same IP within 15 minutes, combined into one risk score.
- **Explainability:** SHAP for the Random Forest; exact deviation from normal for live mode.
- **Live attack-type classifier:** a trained Decision Tree names each live alert (Port scan / Traffic flood / Brute force / Normal) instead of hand-written rules — 99% accuracy on held-out windows. See `live_classifier.py`.
- **Source reputation lookup:** each alerting IP is enriched with its country, network owner and abuse-confidence score (public IPs only; private/lab IPs are never sent out). See `ip_reputation.py`.
- **MITRE ATT&CK mapping and recommended response** for every alert.
- **Analyst actions:**
  - block an IP (replay: later alerts from it are marked Blocked; live: shows the real Windows Firewall command),
  - export alerts as CSV,
  - download an incident report.
- **Model comparison:** 4 algorithms benchmarked on the same test set.

## Risk score

`risk = 100 × (0.60 × network evidence + 0.25 × failed logins + 0.15 × repeat alerts)`

- Network evidence: the model's attack probability (replay), or how far traffic is above this laptop's normal (live).
- Failed logins: from the same IP in the last 15 minutes; 10 or more counts as full.
- Repeat alerts: earlier alerts from the same IP in the last 15 minutes; 5 or more counts as full.

Severity bands: Critical ≥ 80, High ≥ 60, Medium ≥ 40. Medium and above become alerts. Live mode adds one rule: 10 or more failed logins in 15 minutes is at least High.

## Demo script (about 5 minutes)

1. **Replay tab:** press Play, then pause and click a Critical alert. Walk through the SHAP chart, the risk breakdown, the IP timeline, and the MITRE mapping.
2. Find `203.0.113.41` in "Riskiest source IPs". Its timeline shows a password brute-force, a successful login, and attacks continuing afterwards: a likely account takeover.
3. Click **Block** on an attacker IP. Its later alerts become Blocked and the open-alert count drops.
4. **Honest edge case:** IP `10.0.6.186` is an employee locked out of their account (9 failed logins). Most of their traffic stays Low, but at about 09:43 the model wrongly flags one flow as Fuzzers and the failed logins push it to Medium. The timeline shows an internal IP with no other alerts, which is how an analyst would clear it.
5. **Live tab:** laptop B runs `attack_demo.py ... all`. Within seconds a Port scan alert appears, explained as "N refused connections (normal = 0), N ports touched (normal = 1)". It escalates when the brute force starts.
6. **Model report:** explain why Random Forest was chosen, using the comparison table.

## Limitations (say these before you're asked)

- The replay's login log and IP addresses are simulated; UNSW-NB15 has neither.
- In the replay simulation, attacker IPs only send attack traffic, which makes the repeat score stronger than it would be on a real network.
- DoS, Exploits, Analysis and Backdoor look very similar in UNSW-NB15, so the model often confuses their type while still flagging them as attacks.
- Features such as source TTL are unusually predictive in UNSW-NB15 because of how the testbed was built, so real-world accuracy would be lower.
- Live mode monitors one machine only, and learns "normal" from a short window. Unusual but harmless activity (for example a large game download) can raise alerts.
- We first tried an Isolation Forest for live mode. It scored a real port scan barely above normal browsing, because it can't tell "far beyond anything seen" from "at the edge of what was seen". We replaced it with the robust baseline, which is also exactly explainable.

## Files

| File | What it does |
|---|---|
| `common.py` | Shared settings, dataset loading, MITRE ATT&CK mapping |
| `step1_train_model.py` | Compares 4 algorithms, trains and evaluates the Random Forest |
| `step2_simulate_logs.py` | Builds the replay feed and the simulated login log |
| `step3_score_and_explain.py` | Correlation, risk scoring, SHAP explanations (replay) |
| `live_classifier.py` | Trains and applies the live attack-type classifier (Feature 1) |
| `ip_reputation.py` | Source IP reputation / geolocation lookup (Feature 2) |
| `make_result_figures.py` | ROC, precision-recall and model-comparison figures |
| `benchmark_overhead.py` | Measures the security component's performance overhead |
| `run_pipeline.py` | Runs the full build (steps 1–6) |
| `live_monitor.py` | Real-time capture, baseline learning, detection and scoring |
| `login_reader.py` | Reads real failed logins from Windows or Linux |
| `attack_demo.py` | Port scan, brute force and flood, for testing your own laptop |
| `app.py` | Dashboard entry point: sidebar and tabs |
| `ui_replay.py`, `ui_live.py`, `ui_model.py` | One file per dashboard tab |
| `ui_common.py` | Charts, response panel, incident report |

To set up the AbuseIPDB reputation score, get a free key from abuseipdb.com and set it before running the monitor: `set ABUSEIPDB_KEY=your_key` (Windows) or `export ABUSEIPDB_KEY=your_key` (Mac/Linux). Without a key, geolocation still works and the abuse score is simply skipped.

## Dataset

Moustafa, N. and Slay, J. (2015). UNSW-NB15: a comprehensive data set for network intrusion detection systems. *Military Communications and Information Systems Conference (MilCIS)*, IEEE.
