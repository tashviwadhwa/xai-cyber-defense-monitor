# XAI Cyber Defense Monitor

A multi-source threat monitoring system. It combines network traffic with login activity, gives every event a 0–100 risk score, maps it to MITRE ATT&CK, recommends a response, and explains every alert so an analyst can see *why* it fired.

It runs in two modes:

|              | Replay demo                                                                               | Live capture                                                             |
|--------------|-------------------------------------------------------------------------------------------|--------------------------------------------------------------------------|
| Network data | UNSW-NB15: real packets recorded on a lab testbed, attacks generated by a simulation tool | **Real packets** captured on your laptop                                 |
| Login data   | Simulated                                                                                 | **Real** failed logins from Windows (event 4625) or Linux (auth.log)     |
| Detection    | Random Forest trained on labelled attacks (supervised)                                    | Behavioural baseline learned from your own normal traffic (unsupervised) |
| Explanation  | SHAP (TreeExplainer)                                                                      | Exact per-feature deviation from normal                                  |
| Real time?   | No, a replay of pre-scored data                                                           | **Yes**                                                                  |

## Setup (once)

Python 3.10–3.13.

```
cd xai-cyber-monitor
python -m venv venv
venv\Scripts\activate            (Windows Command Prompt)
.\venv\Scripts\Activate.ps1      (Windows PowerShell)
source venv/bin/activate         (Mac/Linux)
pip install -r requirements.txt
```

For live capture on Windows, also install **Npcap** from https://npcap.com/#download (keep the default options).

**Setup problems**

- *PowerShell says running scripts is disabled:* run `Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned` once, then activate again.
- *`pip install` fails with an SSL "certificate has expired" error:* check that the computer's date and time are correct, try another network (college Wi-Fi often intercepts HTTPS), and as a last resort on a trusted network run `pip install --trusted-host pypi.org --trusted-host files.pythonhosted.org -r requirements.txt`.
- *`ModuleNotFoundError` when running a script:* the packages are not installed in the active environment. Activate the virtual environment and run `pip install -r requirements.txt` again.

## Live capture (two laptops on the same Wi-Fi or hotspot)

**Laptop A (monitored)**, in a terminal opened **as Administrator**:

```
python live_monitor.py --learn 10
```

It prints this laptop's IP. For 10 minutes, use the laptop normally (browse, watch a video) while it learns what normal looks like. When it prints `DETECTING`, open a second terminal and run `streamlit run app.py`, then go to the **Live capture** tab.

**Laptop B (attacker)**, a normal terminal:

```
python attack_demo.py <laptop A's IP> scan     # port scan
python attack_demo.py <laptop A's IP> brute    # wrong-password logins over SMB (Windows)
python attack_demo.py <laptop A's IP> all      # both together, which should reach Critical
```

Only ever run `attack_demo.py` against your own devices.

Later runs of `python live_monitor.py` reuse the saved baseline. Use `--relearn` to learn again, for example on a different network.

**If something doesn't show up:**

- *No traffic from laptop B at all:* some phone hotspots isolate devices from each other. Try another hotspot or a Wi-Fi router, and check that `ping <laptop A's IP>` works from B.
- *No failed logins:* make sure Windows records them. In an Administrator terminal: `auditpol /set /subcategory:"Logon" /failure:enable`.
- *SMB brute force doesn't reach laptop A:* the network needs to be set to Private with file sharing on. If that's not possible, type a wrong password at laptop A's lock screen 10 times instead. It appears as a brute force from "local console".
- *Wrong network interface:* run `python live_monitor.py --iface "Wi-Fi"` (use your adapter's name).

## Reproducing the results

Random seeds are fixed (`RANDOM_STATE = 42`), so the replay results and the incident simulation are deterministic. Live-mode results depend on your network and on the baseline your machine learns, so they are reproduced by following the live capture steps above.

```
python run_pipeline.py           # trains 4 models, simulates logs, scores and explains
python make_result_figures.py    # ROC, precision-recall and model-comparison figures
python benchmark_overhead.py     # overhead of detection and explanation
python simulate_incident.py      # Review 3 incident simulation (see below)
```

Outputs are written to `artifacts/` (metrics, figures, scored feed, `overhead.json`, `incident_simulation.json`).

## Results

**Replay model (held-out test set, 52,603 flows)**

| Model                      | Type accuracy | Detection | False alarms |
|----------------------------|---------------|-----------|--------------|
| Logistic Regression        | 76.8%         | 96.7%     | 11.9%        |
| Decision Tree              | 81.4%         | 98.4%     | 14.0%        |
| Gradient Boosting          | 82.4%         | 96.7%     | 8.6%         |
| **Random Forest (chosen)** | **82.4%**     | **97.0%** | **8.4%**     |

The chosen Random Forest reaches ROC-AUC 0.9923 and average precision 0.9963 on attack-versus-normal. Macro-F1 across the ten classes is 0.54: DoS, Backdoor, Analysis and Worms are often confused with neighbouring attack families (low type recall), although the flows are still flagged as attacks.

With correlation in the replay, 99.6% of real attacks raised an alert, and only 3.7% of normal flows did. On the same 3,000-flow feed the Random Forest alone flags 97.2% of attacks and 7.3% of normal flows.

**Live mode (tested with a real port scan and brute-force attempts)** A 1,000-port scan scored about 9 "spreads" above normal (anything above 3 is unusual) and was labelled Port scan. Brute-force sources were flagged High, and normal traffic stayed at a score of 0.

**Overhead** (`benchmark_overhead.py`, see `artifacts/overhead.json`): replay detection costs about 0.02 ms per flow; a SHAP explanation about 44 ms per alert. In live mode, classifying a window takes about 2.7 ms and the exact deviation explanation about 0.02 ms.

## Features

- **Detection:** supervised Random Forest (replay) and an unsupervised behavioural baseline (live).
- **Correlation:** network evidence + failed logins + repeat alerts from the same IP within 15 minutes, combined into one risk score.
- **Explainability:** SHAP for the Random Forest; exact deviation from normal for live mode.
- **Live attack-type classifier:** a trained Decision Tree names each live alert (Port scan / Traffic flood / Brute force / Normal) instead of hand-written rules — 99% accuracy on held-out windows (the training windows are synthetic; see Limitations). See `live_classifier.py`.
- **Source reputation lookup:** each alerting IP is enriched with its country, network owner and abuse-confidence score (public IPs only; private/lab IPs are never sent out). See `ip_reputation.py`.
- **MITRE ATT&CK mapping and recommended response** for every alert.
- **Analyst actions:**

  - block an IP (replay: later alerts from it are marked Blocked; live: shows the real Windows Firewall command),
  - export alerts as CSV,
  - download an incident report.
- **Model comparison:** 4 algorithms benchmarked on the same test set.
- **Incident simulation:** a scaled-down replay of a real-world attack against the working detection code (`simulate_incident.py`).

## Risk score

`risk = 100 × (0.60 × network evidence + 0.25 × failed logins + 0.15 × repeat alerts)`

- Network evidence: the model's attack probability (replay), or how far traffic is above this laptop's normal (live).
- Failed logins: from the same IP in the last 15 minutes; 10 or more counts as full.
- Repeat alerts: earlier alerts from the same IP in the last 15 minutes; 5 or more counts as full.

Severity bands: Critical ≥ 80, High ≥ 60, Medium ≥ 40. Medium and above become alerts. Live mode adds one rule: 10 or more failed logins in 15 minutes is at least High.

## Real-world incident case study (Review 3)

**Incident:** the 2024 Snowflake customer data-theft campaign (UNC5537). Attackers used credentials stolen by infostealer malware to log in to customer cloud data-warehouse accounts that had no multi-factor authentication and no network allow lists, copied out large volumes of data, and extorted the victims. The full write-up (summary, timeline, impact, root cause, ATT&CK mapping, mapping to our Review 1 threat model, gaps and recommendations) is in the Review 3 report.

**Source:** Mandiant (Google Cloud), "UNC5537 Targets Snowflake Customer Instances for Data Theft and Extortion", 10 June 2024 (updated 17 June 2024): https://cloud.google.com/blog/topics/threat-intelligence/unc5537-snowflake-data-theft-extortion

### Scaled-down simulation

`simulate_incident.py` replays the attack chain against this project's own detection code. The baseline training, deviation scoring, risk formula, brute-force rule and attack-type classifier are imported from `live_monitor.py` and `live_classifier.py`, not re-implemented. The traffic is simulated: each stage is injected as the ten-feature window the live monitor would compute from that traffic. Two synthetic baselines (browsing with streaming, and browsing only) are each run over 30 seeds.

```
python simulate_incident.py
```

| Stage | What is injected | Result |
|-------|------------------|--------|
| Valid-credential login from a VPN address | One short session, 0 failed logins | Not detected (0 of 30 runs) |
| Stale credentials, 6 failed logins | Same, 6 failures first | Not detected; risk 15 |
| Stale credentials, 12 failed logins | Same, 12 failures first | High, "Brute force" (30 of 30 runs) |
| Reconnaissance queries | Three short sessions | Not detected |
| Bulk exfiltration, full simulated rate | Six windows of about 4.2 MB each | Alert in only 6–7 of 30 runs; labelled "Traffic flood" |
| Exfiltration at 50% rate or lower | Same, slower | Never alerted |

Stages that happen outside the monitored host (credential theft on a contractor laptop, staging inside the cloud platform, extortion) cannot be observed by this system.

**What this shows:** the system is effective against noisy attacks (scanning, password guessing) and weak against attacks that arrive with valid credentials and little observable network activity. Volume is scored on a log scale, which compresses very large transfers, so a roughly thousand-fold exfiltration reaches only about 5.5 spreads (risk 30–35, below the alert threshold of 40). Proposed improvements: read successful logins and add a first-seen-source rule, raise the score for VPN and hosting networks, add cumulative outbound-volume features and a data-exfiltration class, and ingest SaaS audit logs. These are not yet implemented or validated.

## Demo script (about 5 minutes)

1. **Replay tab:** press Play, then pause and click a Critical alert. Walk through the SHAP chart, the risk breakdown, the IP timeline, and the MITRE mapping.
2. Find `203.0.113.41` in "Riskiest source IPs". Its timeline shows a password brute-force, a successful login, and attacks continuing afterwards: a likely account takeover.
3. Click **Block** on an attacker IP. Its later alerts become Blocked and the open-alert count drops.
4. **Honest edge case:** IP `10.0.6.186` is an employee locked out of their account (9 failed logins). Most of their traffic stays Low, but at about 09:43 the model wrongly flags one flow as Fuzzers and the failed logins push it to Medium. The timeline shows an internal IP with no other alerts, which is how an analyst would clear it.
5. **Live tab:** laptop B runs `attack_demo.py ... all`. Within seconds a Port scan alert appears, explained as "N refused connections (normal = 0), N ports touched (normal = 1)". It escalates when the brute force starts.
6. **Model report:** explain why Random Forest was chosen, using the comparison table.
7. **Case study:** show `python simulate_incident.py` output and explain which stages the system sees and which it misses.

## Limitations (say these before you're asked)

- The replay's login log and IP addresses are simulated; UNSW-NB15 has neither.
- In the replay simulation, attacker IPs only send attack traffic, which makes the repeat score stronger than it would be on a real network.
- DoS, Exploits, Analysis and Backdoor look very similar in UNSW-NB15, so the model often confuses their type while still flagging them as attacks.
- Features such as source TTL are unusually predictive in UNSW-NB15 because of how the testbed was built, so real-world accuracy would be lower.
- The live attack-type classifier is trained on synthetic windows generated from hand-specified feature ranges. Its 99% accuracy is measured on held-out windows from the same generator, so it shows the classes are separable, not that it generalises to arbitrary real traffic.
- Live mode monitors one machine only, and learns "normal" from a short window. Unusual but harmless activity (for example a large game download) can raise alerts.
- Only failed logins are read; successful logins are not used in scoring, so a login with valid credentials is invisible to the monitor.
- Volume is scored on a log scale, so very large transfers are compressed; the incident simulation shows bulk exfiltration often stays below the alert threshold.
- The incident simulation injects synthetic feature windows with synthetic baselines. It tests the real scoring code but not real packet capture; its results should be confirmed on the two-laptop setup.
- We first tried an Isolation Forest for live mode. It scored a real port scan barely above normal browsing, because it can't tell "far beyond anything seen" from "at the edge of what was seen". We replaced it with the robust baseline, which is also exactly explainable.

## Future work

- Read successful logins; add first-seen-source and unusual-location rules.
- Add outbound-volume features and a data-exfiltration class mapped to ATT&CK exfiltration techniques.
- Use network-owner reputation (commercial VPN and hosting networks) in the score.
- Ingest SaaS and application audit logs as a third evidence source.
- Validate on real labelled traffic and newer datasets; learn the risk weights instead of fixing them.
- Extend live mode to multiple hosts.

To set up the AbuseIPDB reputation score, get a free key from abuseipdb.com and set it before running the monitor: `set ABUSEIPDB_KEY=your_key` (Windows) or `export ABUSEIPDB_KEY=your_key` (Mac/Linux). Without a key, geolocation still works and the abuse score is simply skipped.
